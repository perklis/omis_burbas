# Монитор здоровья — настольный прототип

Прототип обычного desktop-приложения **MyHeath** на Python и Tkinter по отчету «Отчет_ОМИС_Лаба_1.docx». Сохранена объектная модель базовой диаграммы: `Main`, `AppInjector`, отдельные `MainWindow`, `ProfileWindow`, `DevicesWindow`, `ReportWindow`, сервисы, интерфейсы, `LocalStorage`, анализатор и модели предметной области. Основное окно сделано в формате desktop-панели: боковая навигация, карточки показателей за сегодня и блок подключенных устройств. До подключения устройства показатели скрыты. Вторичные сценарии открываются отдельными окнами.

## Запуск

Нужен Python 3 с Tkinter (в некоторых Linux-дистрибутивах Tkinter устанавливается отдельным системным пакетом). В корне проекта выполните:

```bash
python3 main.py
```

Сторонние Python-библиотеки не требуются. Профиль, состояние демонстрационных устройств и история измерений сохраняются в `~/.health_monitor/data.json`.

## Объектная модель и вызовы

`Main.main()` из диаграммы представлена `Main.run()` и создает `AppInjector`; injector отдельно создает UI окна и зависимости. `LocalStorage` реализует `IProfileStorage`, `IDeviceStorage`, `IMetricStorage`; `StatisticalDataAnalyzer` реализует `IDataAnalyzer`, `BluetoothConnector` — `IDeviceConnector`.

- `MainWindow` открывает независимые `ProfileWindow`, `DevicesWindow`, `ReportWindow` через `AppInjector`.
- `ReportWindow` вызывает `IDataAnalyzer.build_report(metric_type, period)`. `StatisticalDataAnalyzer` запрашивает записи у `IMetricStorage`, считает среднее/минимум/максимум и возвращает `Report`; UI строит график, гистограмму по выбранным значениям и показывает пустое состояние при отсутствии данных.
- `ProfileWindow` передает `UserProfile` в `ProfileService`; сервис валидирует профиль и сохраняет его через `IProfileStorage`.
- `DevicesWindow` получает и выбирает `DeviceInfo` через `DeviceManager`. Тот вызывает `IDeviceConnector.pair/unpair/fetch_metrics` и сохраняет изменения через `IDeviceStorage` и `IMetricStorage`.

Код разнесен по `health_monitor/domain.py`, `interfaces.py`, `storage.py`, `services.py`, `injector.py`, `ui.py`.

## Проверка соответствия перечню классов и четырем подсистемам

Проверено и скорректировано по состоянию кода на 22.11.2026. Модели содержат идентификаторы, `TimePeriod` задает даты начала/окончания, `SleepData` наследует `HealthMetric`, `SleepReport` содержит фазы, а `Report` — временной словарь `scores`. Обработчики UI и `Main.main()` добавлены. Среднее, минимум и максимум оставляются незаполненными при одной или нулевой записи.

| Подсистема / группа | Совпадает | Расхождения и текущее поведение |
|---|---|---|
| Связь с гаджетом | Есть `IDeviceConnector`, `BluetoothConnector`, `DeviceManager`; сопряжение и запрос измерений проходят через них. | Bluetooth имитируется случайными значениями. `pair/unpair/fetch_metrics(device)` отличаются от заданных `pair_device(device)/unpair(device)/fetch_metrics()`. `DeviceManager.synchronize(device)` требует аргумент, тогда как в перечне `synchronize()`. Сканирование возвращает два демонстрационных устройства. |
| Хранение | Есть все три интерфейса и `LocalStorage`; профиль, устройства и измерения пишутся в JSON локально. | Облака нет. На первом запуске `LocalStorage` создает год случайной демонстрационной истории даже до подключения гаджета; после подключения она становится видимой до первой синхронизации. Измерения сохраняются как словарь «дата → тип → значение»: повторное измерение того же типа за день затирает предыдущее, точное время и ID измерения теряются. Поэтому обещанная история измерений любой подробности не обеспечивается. |
| Анализ | `IDataAnalyzer.build_report` и `StatisticalDataAnalyzer` загружают записи через `IMetricStorage`; строятся среднее, минимум, максимум и UI-график. | Внутренний `Report` сейчас хранит `period`, список `values` и агрегаты, но не заданные `id` и `scores: Dict[DateTime, Real]`. UI строит график из `values`, а не из `scores`. Среднее/минимум/максимум рассчитываются даже при одной записи, вопреки примечанию к диаграмме, что их заполнять только при `scores` больше 1. `calculate_sleep_score` принимает объект с `duration_hours`, а диаграмма описывает `SleepData` с фазами. |
| Интерфейс | Реализованы отдельные `MainWindow`, `ProfileWindow`, `DevicesWindow`, `ReportWindow` и выбор показателя/периода. | Часть операций имеет другие имена/формы: у `MainWindow` нет явного `on_sync_clicked` и `show_sync_result`; у `ProfileWindow` нет `on_edit_clicked`/`show_error`; у `DevicesWindow` нет отдельных `on_scan_clicked`, `on_connect_clicked`, `on_disconnect_clicked`, `on_sync_clicked`; у `ReportWindow` нет обработчиков `on_metric_selected`, `on_period_selected`, `on_build_report_clicked`, `show_report`. Действия выполняются непосредственными callback-методами. |
| Main / Injector | Есть `Main`, `AppInjector` и все перечисленные фабричные методы injector. | Точка входа названа `Main.run()`, а в перечне — `Main.main()`. Фабрики окон принимают дополнительные `parent`/callback параметры для Tkinter. |
| DTO и enum | Есть `MetricType` со всеми четырьмя значениями; есть `UserProfile`, `DeviceInfo`, `HealthMetric`, `NumericMetric`, `SleepData`, `TimePeriod`, `Report`, `SleepReport`. | Поля отличаются: нет `id` в `UserProfile`, `DeviceInfo`, `HealthMetric`, `Report`; `UserProfile` содержит дополнительный `gender`, а `height_cm/weight_kg` вместо `height/weight`; `DeviceInfo` хранит `connected/source`, но не ID; `HealthMetric` хранит `type/value/recorded_at`, но не `measured_at/device_id`; `SleepData` не наследует `HealthMetric` и хранит только длительность; `TimePeriod` сейчас enum предустановленных длительностей вместо объекта с `start_date/end_date`; `Report` не содержит `scores`; `SleepReport` не содержит `phases`. |

### Фактическая цепочка данных

При синхронизации `DevicesWindow → DeviceManager → BluetoothConnector.fetch_metrics → LocalStorage.save_metrics`. При запросе отчета `ReportWindow → StatisticalDataAnalyzer.build_report → LocalStorage.load_metrics → Report → график/сводка`. Профиль идет по цепочке `ProfileWindow → ProfileService.validate/update_profile → LocalStorage.save_profile`. Это связывает четыре подсистемы, но ограничение хранилища по одному значению на показатель в сутки и демонстрационный connector выше мешают считать поток полностью соответствующим текстовому обещанию о необработанной истории измерений за любой период.

## Реализованные сценарии

- Главная показывает сегодняшние значения пульса, шагов, калорий и сна.
- Показатели отображает динамику за день, неделю, месяц или год, а также среднее, минимум и максимум.
- Профиль позволяет просматривать и редактировать имя, пол, возраст, рост и вес.
- Устройства позволяет подключать/отключать Smart Band 9 и Galaxy Watch 7; для подключенного устройства доступна демонстрационная синхронизация.
- После синхронизации формируются демонстрационные значения, которые попадают в локальную историю.

## Соответствие отчету и известные ограничения модели

Реализация следует базовым сценариям и сущностям отчета, включая неполноты и несогласованности диаграмм. Существенные ошибки самого отчета и исходный разбор сохранены в [АНАЛИЗ_И_ОШИБКИ.md](АНАЛИЗ_И_ОШИБКИ.md).

| Материал отчета | Как отражен в прототипе |
|---|---|
| ER-диаграмма | Пользовательский профиль, устройства, четыре показателя и отчётная статистика представлены данными профиля, устройств и истории измерений. Сон представлен числом часов, отдельные фазы сна в ER-модели не показаны в интерфейсе. |
| BPMN | Общий поток «подключение/синхронизация → сохранение → анализ → отображение» реализован действиями интерфейса. Разветвленная BPMN-диаграмма не задает однозначно все ошибки и условия; отсутствующие ветви не додумывались. |
| Варианты использования | Просмотр динамики, выбор показателя/периода, просмотр/изменение профиля, подключение/отключение и синхронизация доступны пользователю. |
| Sequence | Сценарии отображения отчета, сохранения профиля и синхронизации выполнены через соответствующие операции UI. Имена участников и методов на sequence диаграмме не везде совпадают с базовой диаграммой классов; поведение реализовано по описанному действию, а расхождения отмечены в анализе. |
| Базовая диаграмма классов | Концепты Main, AppInjector, UI, хранилище, профиль, устройство, измерение, анализатор и отчет представлены модулями/классами в одном desktop-прототипе. Отдельные UML-интерфейсы и зависимости не воспроизводятся буквально там, где диаграммы расходятся или не задают сигнатуру. |
| ИИ, новые источники, тренировки | Это направления развития, а не часть базового функционала. В отчетных расширениях есть противоречие принципу расширения без изменения базовых классов; в прототип не добавлены, чтобы не менять описанную базовую систему. |
| Диаграмма состояний UI и макеты | Отдельные окна профиля, устройств и анализа открываются из главной панели. Для отключенного устройства показывается предложение подключить гаджет вместо показателей. Схема адаптирована под рабочее окно компьютера. |

### Замеченные ошибки и пробелы диаграмм

- Sequence использует участника «Устройства» и русские названия операций, которые не совпадают с классами и методами базовой диаграммы классов.
- ER не выделяет профиль отдельной сущностью и не показывает явно датированные измерения/историю синхронизации; связи, кратности и модель «тип показателя — измерения» местами неоднозначны.
- BPMN перегружена ветвлениями и мелкими элементами, поэтому детали отдельных условий не всегда читаются.
- Use case требует ясной границы системы; связь `include` между просмотром динамики, выбором показателя/периода и построением графика не полностью пояснена.
- Диаграмма состояний UI местами не связывает переходы с операциями UI-классов и макетами загрузки/ошибки.
- Базовая диаграмма классов не везде показывает сигнатуры, атрибуты, кратности и использование интерфейсов; русский и английский языки имен смешаны.
- Диаграммы расширений ИИ и тренировок меняют `AppInjector` и `LocalStorage`, хотя заявлен принцип расширения без модификации базовых классов.

Эти пункты не исправлялись путем изменения предметной модели: реализация следует отчету настолько, насколько тот определяет поведение. Неописанные операции и ветви не трактуются как полноценные требования. Полный исходный разбор с оценкой серьезности находится в сохраненном файле анализа.

## Границы прототипа

Физический Bluetooth, облачная синхронизация, медицинская интерпретация и рекомендации ИИ в отчете не определены достаточно для настоящей реализации. Подключение и передача значений поэтому демонстрационные; данные не являются медицинскими. Настольная реализация выбрана по запросу пользователя, хотя исходные макеты визуально изображают мобильное приложение.
