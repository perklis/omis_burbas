## О чём система и как выглядит приложение

Это мобильный трекер здоровья. Пользователь задаёт профиль (имя, пол, возраст, рост, вес), подключает носимые устройства, синхронизирует пульс, шаги, калории и сон, а затем смотрит показатели по периодам и графики. В отчёте перечислены четыре подсистемы: связь с устройством, хранение, анализ и UI. Отдельно описаны три расширения: советы на основе ИИ, новые источники показателей и тренировки.

Макеты выполнены в тёмной теме с зелёными акцентами и нижней панелью вкладок. Представлены экраны «Главная», «Показатели» (графики пульса/шагов и выбор периода), «Профиль» и «Устройства» (список, подключение, отключение, пустое состояние); показаны просмотр и редактирование профиля, ошибка подключения. Это хороший ориентир для визуальной части. Макеты похожи на iPhone, но описанная модель не задаёт платформу или конкретный SDK.

## Что установить для реализации похожего мобильного приложения

Рекомендую **Android Studio + Java + Android SDK**. Java прямо входит в разрешённый преподавателем список, а Android Studio даёт редактор, сборку, Android SDK, эмулятор и средства запуска приложения. Для лабораторного прототипа можно сделать Activity для экранов и переключение через нижнюю навигацию; содержимое графиков и синхронизацию оставить демонстрационными, если внутренняя логика не требуется.

Установить:

1. **Android Studio** — среда разработки.
2. В Android Studio через **SDK Manager** — актуальные Android SDK Platform и Android SDK Build-Tools; **SDK Platform-Tools** (включая `adb`).
3. Через **Device Manager** — образ Android Emulator и виртуальное устройство. Можно вместо эмулятора включить на телефоне режим разработчика и USB debugging.
4. **Git** — для локальной фиксации исходников и отправки проекта на GitHub. Аккаунт GitHub нужен, чтобы создать репозиторий и опубликовать ссылку в отчёте.

Отдельный JDK обычно ставить не нужно: Android Studio поставляется с JBR, который подходит для Gradle. При необходимости проверки на iPhone следует отдельно решить вопрос с macOS/Xcode; Java-проект для Android сам по себе не создаёт iOS-приложение.

## С чего начать реализацию

Сначала реализовать базовую версию по основной диаграмме: модель профиля и измерений, интерфейсы хранилища/подключения, простой локальный репозиторий, анализатор и экраны с переходами. После сверки UML с преподавателем оформить каждое направление развития отдельной веткой архитектуры. Сбор данных Bluetooth можно заменить демонстрационными данными, если для защиты важны только запуск приложения и навигация между окнами.





Нарушение п. 7.1: Базовая диаграмма классов содержит методы create_main_window, create_profile_window, create_connector и т.д. в классе AppInjector. Это нормально для инжектора. Однако, если классы из направлений развития (например, AIAnalyzer или TrainingService) не упоминаются в базовой, то это выполнено. Но на базовой диаграмме присутствует класс LocalStorage, который реализует три интерфейса: IDeviceStorage, IMetricStorage, IProfileStorage. Выделенные интерфейсы должны использоваться, но реализация всех трех интерфейсов одним классом может нарушать принцип единственной ответственности, хотя формально это не запрещено.


Нарушение п. 7.12 (Навигация): На диаграмме классов направления развития ИИ (стр. 8) между AIAnalyzer и StatisticalDataAnalyzer стоит связь <<use>> с навигацией. Согласно п. 7.11, если есть зависимость <<use>>, должно быть понятно, как класс узнает о другом. Здесь просто стрелка, без указания параметра метода или ассоциации. Также на стр. 7, класс MainWindow имеет зависимость <<use>> к DeviceManager, IDataAnalyzer, ProfileService, но не показано, как именно он их использует (через параметры методов или атрибуты).

Нарушение п. 7.8 (Инжектор): Класс AppInjector (стр. 7) имеет зависимости <<create>> к классам. Это выполнено. Но класс Main (стр. 7) имеет зависимость <<create>> к AppInjector. Согласно п. 7.8, класс <<main>> может совпадать с <<injector>>, но здесь они разделены, что допустимо. Однако, если Main создает AppInjector, то Main должен знать о AppInjector, что является зависимостью, а не просто <<create>> без указания параметров.

Нарушение п. 7.24 (Наследование): На диаграмме классов направления развития «Расширение набора источников данных» (стр. 8) класс WifiConnector наследует IDeviceConnector. В WifiConnector указаны методы + scan_devices(), + pair_device(), + unpair(), + fetch_metrics(), + supportSource(). Это правильно, так как они переопределяются. Но в классе CloudHealthConnector указан атрибут + api_token: String, а в FlatSportConnector — + file_path: String. Это новые атрибуты, что допустимо.

Нарушение п. 7.20 (Единственная ответственность): Класс MainWindow (стр. 7) содержит методы для работы с устройствами (on_open_devices_clicked), профилем (on_open_profile_clicked) и отчетами (on_open_report_clicked). Это нарушает принцип единственной ответственности, так как окно должно только отображать и делегировать действия, а не управлять логикой всех подсистем. Хотя это UI-класс, он имеет слишком много зависимостей.

На диаграмме последовательности (стр. 6) есть объект Интерфейс, Система создания отчетов, Подсистема анализа данных, Хранилище данных.

🔴 Ошибки в разделе «Диаграмма вариантов использования» (п. 5)
Нарушение п. 5.1 (Акторы должны быть внешними сущностями):

На диаграмме вариантов использования (стр. 5) актор «Носимый гаджет» является внешней сущностью, это верно. Актор «Владелец носимого устройства» — тоже внешний.

Ошибка: В варианте использования «Синхронизировать данные с устройством» актор «Носимый гаджет» связан с этим вариантом. Но согласно текстовому описанию, синхронизацию инициирует пользователь через интерфейс. Гаджет является пассивным источником данных. Связь актора «Гаджет» с вариантом использования «Синхронизировать данные» может быть неверной, так как гаджет не инициирует этот процесс.

Нарушение п. 5.3 (Варианты использования должны включать действия от начала до завершения):

Вариант использования «Просмотреть динамику показателя за период» включает <<include>> к «Выбрать показатель», «Выбрать период», «Построить график/гистограмму». Это правильно. Но вариант «Просмотреть профиль» имеет <<extend>> от «Изменить профиль». Это тоже допустимо. Однако, вариант «Подключить новое носимое устройство» не имеет завершающего действия (например, «Подтвердить подключение»). Он выглядит как простое действие.

🔴 Ошибки в разделе «ER-диаграмма» (п. 3)
Нарушение п. 3.2 (Множители и названия связей):

На ER-диаграмме (стр. 4) между сущностями «Пользователь» и «Носимый гаджет» стоит связь «Имеет» с множителями 1:N. Это верно.

🔴 Общие ошибки (п. 1)
Нарушение п. 1.3 (Цветовое выделение должно иметь смысл):

На диаграммах классов (стр. 7, 8, 9) используется цветовое выделение: голубой для UI, зеленый для интерфейсов, желтый для данных, оранжевый для инжектора. Это имеет смысл. В тексте используются русские названия («Пользователь», «Носимый гаджет», «Показатель здоровья»), а на диаграммах классов — английские (UserProfile, DeviceInfo, HealthMetric). Это нарушение п. 1.4.
